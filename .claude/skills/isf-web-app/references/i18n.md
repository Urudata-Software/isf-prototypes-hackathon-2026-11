# Internationalization (i18n)

## Approach

`next-intl` **without URL-based routing** — every route stays at `/documents`,
`/dashboard`, and the locale never appears in the URL.

A POC ships **one language**: the client's. It still goes through next-intl, so
adding another later is a new file rather than a rewrite.

## Which language the app runs in

`appLocale` in `src/i18n/locale.ts`, read by `src/i18n/request.ts`. One constant.

```ts
// src/i18n/locale.ts
export const locales = ['en', 'es'] as const
export type Locale = (typeof locales)[number]

export const appLocale: Locale = 'es'
```

```ts
// src/i18n/request.ts
export default getRequestConfig(async () => ({
  locale: appLocale,
  messages: (await import(`../../messages/${appLocale}.json`)).default,
}))
```

It is deliberately **not** detected from `Accept-Language`. A POC is demoed on
whatever laptop is in the room, and a demo that changes language depending on that is
a defect. `<html lang>` follows `appLocale` automatically through `layout.tsx`.

## Changing the language

1. Set `appLocale` in `src/i18n/locale.ts`.
2. Make sure `messages/<locale>.json` holds every key.
3. Delete the message file you are not using.

## Adding a second locale

Rare, and only when a POC genuinely has to show two languages. Add the code to
`locales`, create `messages/<code>.json` with the same key structure, and restore
per-request selection in `request.ts`.

## Adding messages for a new module

Add a new top-level namespace key to every locale file. The key matches the plural feature name:

```json
{
  "documents": { ... },
  "products": {
    "title": "Products",
    "newProduct": "New Product",
    "back": "← Back",
    "backToList": "Back to Products",
    "count": "{count, plural, one {# product} other {# products}}",
    "noResults": "No products found.",
    "notFound": "Product not found",
    "table": {
      "name": "Name",
      "price": "Price",
      "status": "Status",
      "actions": "Actions",
      "edit": "Edit",
      "delete": "Delete"
    },
    "form": {
      "newTitle": "New Product",
      "editTitle": "Edit Product",
      "name": "Name",
      "price": "Price",
      "status": "Status",
      "saving": "Saving…",
      "createSubmit": "Create Product",
      "editSubmit": "Save Changes"
    }
  }
}
```

Keep all locale files in sync — every key that exists in `en.json` must exist in every other locale file.

## ICU message format

Use ICU syntax for plurals and interpolation:

```json
"count": "{count, plural, one {# product} other {# products}}"
```

Called as: `t('count', { count: totalCount })`

## Using translations in components

### Server Components

```tsx
import { getTranslations } from 'next-intl/server'

export default async function ProductsPage() {
  const t = await getTranslations('products')
  return <h1>{t('title')}</h1>
}
```

Access nested keys with dot notation: `t('table.name')`, `t('form.editTitle')`.

### Client Components

```tsx
'use client'
import { useTranslations } from 'next-intl'

export function ProductForm() {
  const t = useTranslations('products.form')
  return <Label>{t('name')}</Label>
}
```

The form component scopes its translations to `'products.form'` and owns all its translation keys internally — no translation props passed in from the parent.

### Dates and formatting

```tsx
import { getLocale } from 'next-intl/server'

const locale = await getLocale()
new Date(value).toLocaleDateString(locale)
// or with currency:
price.toLocaleString(locale, { style: 'currency', currency: 'USD' })
```

### Root layout — how Client Components receive messages

`src/app/layout.tsx` calls `getLocale()` and `getMessages()` and wraps children in `NextIntlClientProvider`. Client Components access messages through this provider — no prop drilling.

```tsx
// src/app/layout.tsx (simplified)
export default async function RootLayout({ children }) {
  const locale = await getLocale()
  const messages = await getMessages()
  return (
    <html lang={locale}>
      <body>
        <NextIntlClientProvider messages={messages}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  )
}
```

## What NOT to do

- Do not hard-code locale strings (e.g. `'en'`) anywhere outside `src/i18n/locale.ts`.
- Do not call `getTranslations` in Client Components — use `useTranslations` instead.
- Do not import message JSON files directly in components — always go through next-intl APIs.
- Do not use `submitLabel` or similar translation props — components own their own translation keys.
